# VWS テロップファイル (.ts1) 構造メモ（非公式・解析中）

2 種類のサンプルをもとに解析した結果です。

| 呼び名 | 内容 | 裏付けに使えるもの |
|---|---|---|
| **見本** | 単一行 16 字・ニューロダン B 100px・白文字＋青縁 6px（内蔵フォント番号 1119） | VWS の書き出し PNG（画素単位で照合） |

### XTRS（イン/アウト効果）

`kind` 1〜4 × `dir` 0(イン)/1(アウト) の 8 件。サンプルで位置を持つのは kind 1 だけ。

| オフセット（ペイロード） | 値 | 意味 |
|---|---|---|
| +0 | u16 1 | ver |
| +2 | u16 1〜4 | kind（対象） |
| +4 | u16 0/1 | イン / アウト |
| +8 | u32 30 | 長さ（フレーム） |
| +12 | u32 1 | 不明 |
| +24 | u16 2/0 | 2 = 移動あり（このとき続けて 24.8 ×6 = 位置A(x,y,z), 位置B(x,y,z)）|
| 続き | u8 0, u32 100 ×6 | 倍率 %（開始/終了 × xyz?） |
| 続き | 0×23, u16 100, u16 100 | 不透明度 %（開始/終了?） |
| 末尾 | VIDT (32B, 全 0) + 4B | 未解明。別サンプルには VIDT が無い（省略できる） |

位置A = テロップの位置 (134, 1042)、位置B = 位置A + MVP_ の移動量（イン: y 992 / アウト: y 1092）。
= 「上から 50px スライドイン、下へ 50px スライドアウト、各 30 フレーム」と読める（推定）。

終端（文字コード 0）や改行にも ACSP が付くことがある。

特別な文字コード: `U+000D` = 改行（空の字形を持つ）、`U+E73E` = 専用の空白（空の字形、送り 512 = 全角の 1/4）、`U+0000` = 終端。

## フォント

.ts1 のフォントの持ち方は 2 通りあります。

- **内蔵番号**（見本）: `ACTP` と各グリフに VWS 内部のフォント番号（1119 = 0x45F）があるだけで、フォント名は入っていない。
- **フォント表つき**（別サンプル）: 番号は 0xE8A1DFA0 のような 32bit 値で、`ODTT` に 番号 → 太さ・文字セット・書体名「FOT-ロダン Pro B」・
  PostScript 名「RodinPro-B」が入っている。番号の決め方は不明（書体名の CRC32 / FNV / MD5 / SHA1 などの一般的なハッシュではない）。

送り幅は字形ごとの ABC 幅（A + B + C）で決まる。全角は 2048、専用空白 U+E73E は 512。半角文字もこの値で送られるはず（推定）。

VWS は表示にはファイル内の字形データを使い、フォント名の表示・打ち替えには番号を使う
（番号を変えずに字形だけ別フォントにした .ts1 は「見た目は変わるがフォント名は元のまま」になった）。

**見本の 1119 = フォントワークス「ニューロダン B」**（特定済み）。
フォントワークス公式の書体見本（試し書き）で同じ 15 文字を表示し、TS1 内の字形と重ね合わせた結果、
一致度 97.2%（全文字 93% 以上、縦横比 1.000）。同ファミリーの DB / EB は 77%、ニィス全 38 書体は最高 81%
（ウインクスL7 は 70%）で、B だけが突出して一致した。

番号 ⇄ フォントの対応は、字形の照合で求める（`run.py identify` / `fontid.py`）:
PC の全フォントについて TS1 の文字の輪郭を塗りつぶして重なり（IoU）を比べ、95% 以上なら一致。
一致したフォントについては「フォント単位 → 2048 セル」の倍率とオフセットも実測して `フォント表.json` に保存する。

PC（ニューロダン Pro B 入り）での照合結果（2026-11-12）: `FOT-NewRodinPro-B.otf`（PostScript 名 `NewRodinPro-B`）が **99.3%**、
次点はロダンカトレア B 83.4%、ロダン ProN B 81.5%、ニューロダン EB 79.6%。
実測した変換は scale 2.048368、ox −0.58、**oy −183.26**（2048 セル単位）。

### ベースラインのずれ（確認済: Photoshop の描画と照合）

VWS のセルのベースライン（CSML.y、グリフ y=0）は、フォント本来のベースラインと一致しない。
ニューロダン B では、フォントのベースラインがセルのベースラインより **183.26/2048 セル上**（100px で 8.95px 上）。
→ Photoshop のテキストのアンカー y = CSML.y + oy × 文字サイズ / 2048（見本: 1042 → 1033.05）。PSD → TS1 は逆に引く。
これを入れないと Photoshop の文字が一律 9px 下にずれる。oy はフォントごとに違う可能性があるので `フォント表.json` の値を使う。

### Photoshop 側の注意（確認済）

- Photoshop の既定のカーニング「メトリクス」は、かなのペアを詰める（見本 16 文字で合計 14px、オプティカルだと 51px）。
  VWS は全角を常に文字サイズ送りで並べるので、JSX ではカーニングを「0（手動）」にしている。
- PSD の文字スタイル（EngineData）にはカーニング方式の区別が残らない（手動でも `AutoKerning: True`）。
  効いた結果は TySh の `bounds`（組み幅）に出るので、PSD → TS1 ではこれを「全角送り＋トラッキング」の計算幅と比べて、
  2px 以上狭ければ警告する。
- VWS の描画位置の癖 (-0.125, -0.375)px は、Photoshop との直接照合でも縦 +0.42px として確認できた（アンカーで補正）。
- Photoshop のアンチエイリアスは STRONG が VWS に最も近い。境界線の太さは Photoshop が保存時に整数へ丸める。
- 見本の往復（TS1 → JSX → Photoshop → PSD → TS1）で、各文字の位置は ±1px、縁込みの範囲は ±1px、
  元の TS1 の描画との重なりは 99.0%。元と違うのは OFRI の左端 1px と、値 0 の冗長な ACSP が 1 か所無いことだけ。

## RCHR / WVCT（グリフ）（確認済）

Windows GDI `GetGlyphOutline(GGO_NATIVE)` とほぼ同じ形式で、セル高 2048（ascent 1802 + descent 246）。
座標は整数、y は下向き（ベースライン = 0）。

"WVCT" u32 (size-8) | u32 輪郭データ長 | 60B ヘッダ | 輪郭…
  ヘッダ: u16 輪郭数, u16 1, bbox(l,t,r,b) 24.8 ×4, u16 2048, u16 2048, u16 黒枠幅, u16 黒枠高,
          u32 フォント番号, u32 文字コード, i32 ascent, i32 -descent, ABC幅 (A,B,C), u32 0
  輪郭:   u32 1, u32 以降のバイト数, i32 x, i32 y (始点)

## レイアウト・描画（見本画像とのピクセル照合で確認済）

- 文字送り = 字形の (A + B + C) / 2048 × 文字サイズ × 横倍率（全角 2048 = 文字サイズぶん、専用空白 U+E73E は 512）。
  ACSP は「その文字の直前」の間隔に加算
- 行の幅 = 送りの合計 + 2 文字目以降の ACSP の合計。行は CSML.x から幅 CSTR.width の枠で **中央揃え**
- CSML.y が最終行のベースライン。行送り = 文字サイズ + ALSP
- グリフは 2048 セル → 文字サイズ px に縮小（ACMG の倍率があれば横・縦それぞれ掛ける）
- 塗りは非ゼロ規則（見本では偶奇規則でも同じ結果）

### VWS の描き方（VWS 出力 PNG の画素値から特定。`vwsrender.py` に実装）

見本（16 字・100px・縁 6px）で、色のある 120,056 画素のうち **VWS の PNG と違うのは 2 画素（差 2/255）だけ = 99.998% が完全一致**。
以下の 1〜8 をこの順に行う。単位は「8 倍格子」= 1px を 8 等分した整数。

1. **字の原点**: 横 = (行の先頭字の x + (その字の x − 先頭字の x) × 0.9999) × 8 を四捨五入、縦 = ベースライン y × 8 を四捨五入。
   1 字の送りが 100px ではなく 99.99px ぶんで、見本では 7 字目から 1/8px 左へずれる（0.99991 / 0.99989 では合わない）
2. **輪郭の点**: `(int)(座標 × 文字サイズ × 8 / 2048)`。C の整数変換 = 0 方向へ切り捨て（字の原点からの相対座標で）
3. **曲線**: 2 次ベジェ (p0, c, p1) を整数のまま半分ずつに割る。
   - 割るかどうか: `h = p0 + (p1 − p0) / 2 − c`（弦の中点と制御点の差。割り算は C の整数割り算 = 0 方向へ切り捨て）を x・y それぞれ求め、
     **hx² + hy² > 17 なら割る**（17 は割らない・18 は割る、まで確認。しきい値は 17 以上 18 未満）
   - 割り方: `q0 = (p0 + c) / 2`、`q1 = (c + p1) / 2`、`r = (q0 + q1) / 2`（どれも足してから 2 で割る整数割り算）→ (p0, q0, r) と (r, q1, p1) に同じ処理
   - 割らないときは p0 → p1 を直線で結ぶ
   - 判定に `p0 − 2c + p1`（2 階差分）を使う書き方や、中点を `p0 + (c − p0) / 2` で作る書き方では合わない（奇数のときの丸めが違う）。
     見本の曲線 309 本・「割る/割らない」が画像から確かめられる 702 か所が、上の式で 1 つの例外もなく説明できる
4. **塗り**: できた多角形を 8 倍サイズで GDI と同じ規則で塗る（整数座標の点が内側なら塗る。左と上の辺は含み、右と下は含まない）
5. **1 ラインぶんの文字面** m = 1 画素の 8×8 = 64 点のうち塗られた数（0〜64）
6. **上下 2 ラインを足す**: k[y] = m[y] + m[y+1]（0〜128）。横の辺は半透明が 1 画素、縦方向の辺は必ず 2 画素にまたがる。
   字ごとに上端を整数行に丸め（上端の px − 0.5 を切り上げた行の 1 行上から描く）、それより上にはみ出す行は切る
7. **縁**: 丸い縁ではない。**文字面 k を 1px 刻みでずらしたコピーの最大値**。ずらし量は i² + j² ≤ (縁 + 0.5)² の全整数点。
   縁 6px なら i² + j² ≤ 42 で、輪郭は (±6, 2) (±5, 4) (±4, 5) (±2, 6) の階段になる（41 ≤ R² < 45 のどれでも同じ。**他の縁幅では未確認**）
8. **色**: RGB = 切り捨て(縁色′ + (文字色′ − 縁色′) × k / 128)、アルファ = min(255, 2 × 縁の k)。
   色′ = 8bit 値 + (R: 0.902 + 0.043 × 値/255、G: 0.81、B: 0.10 − 0.01 × 値/255)。見本に出てくる 129 色すべてが再現できる

残る 2 画素は「な」の輪郭の先端の 1 点（8×8 のうちの 1 点。輪郭を閉じる辺と最初の曲線がつながる頂点ちょうどの点）で、
VWS は塗っておらず、本物の GDI は塗る。VWS が GDI そのものではなく自前の塗り処理を使っている可能性があるが、1 例だけなので規則は不明。
