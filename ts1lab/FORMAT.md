# VWS テロップファイル (.ts1) 構造メモ（非公式・解析中）

サンプル 1 件（単一行・16 文字）と、その VWS 出力画像（透過 PNG）をもとに解析した結果です。
「確認済」は解析→再構築のバイト一致、または VWS 出力画像とのピクセル照合で裏付けが取れたもの、
「推定」はまだ裏付けがないものです。

## 共通ルール（確認済）

| 項目 | 内容 |
|---|---|
| エンディアン | リトルエンディアン |
| チャンク | 4 文字タグ + `u32` サイズ（ヘッダ 8 バイトを含む）+ ペイロード |
| 例外 | `WVCT` のサイズはヘッダ 8 バイトを含まない。`ESET` は `"ESET" + u32 0 + u16 件数` の 10 バイト固定。`EMTR` は `"EMTR" + u32 文字コード + 12 バイト 0` の 20 バイト固定 |
| 数値 | 座標・サイズの多くは **24.8 固定小数点**（`i32 / 256`） |
| 文字列 | `u8 長さ`（0 のときは続く `u16` が長さ）+ `FF FE` + UTF-16LE + `00 00` |

## ツリー

全バイトを項目に割り当て済み（`ts1tool.py dump` で一覧、漏れがあるとエラーになる）。

```
TSRC  (8B: 00 01 00 01 00 00 00 00 = 版?)
└ SWRK  u16 ver, u32 書き出し時刻(UNIX), u32 ID?（チェックサムではない: CRC32/Adler/和 いずれも不一致）
  ├ OFRI   u16 40?, u16 3?, 24.8 113.0（= 文字高 100 + 縁 6×2 + 1 と一致・推定）, 0×18,
  │        描画範囲 (left, top, right, bottom) 24.8 … 縁込みのインク範囲（確認済）
  ├ OOCI / OOCO  +12 に u32 60（イン/アウト側の長さ?）、他は 0
  ├ OMR0   編集履歴: u16 ver, u16 0, u16 件数, [u32 ID, u32 UNIX時刻, 文字列 ユーザー, 文字列 操作]…（確認済）
  ├ ORMP   リソース表: u16 ver, u16 件数, 以下の配列（確認済）
  │  ├ RCHR × n   グリフキャッシュ（先頭は空グリフ = 終端用。本文の末尾の文字から順に登録）
  │  │  └ WVCT    アウトライン
  │  ├ CRGB × 2   色: u16 ver, u32 種別(1 = 単色), **R G B A**。サンプルは 白 #FFFFFF / 縁 #E72F12（赤）
  │  │            ※ 渡された VWS 出力 PNG では縁が青 #122FE7 → PNG 書き出し時に R/B が入れ替わっている模様
  │  └ ORSC × 2   u16 ver, u32 0（未解明。装飾 2 件に対応?）
  ├ ESET (レイヤ数 1)
  └ SLYR  レイヤ: 文字列 名前（"基底レイヤ"）, u16 0, ESET(1)
     └ CSML  文字列ブロック: u16 ver, 24.8 x, 24.8 y, i32 -1, u16 0, u16 1
        │      x = 文字枠の左端, y = ベースライン（見本画像で確認済）
        ├ XTRS × 8   イン/アウト効果（下表）
        ├ MVP_ × 2   u16 ver, u16 2, 24.8 ×4 = (0, 0, 0, 移動量)。イン -50 / アウト +50
        ├ 3FLG, GROP, GRAP, LGOP, FRTV, EVEB, SRSC   未解明（値は dump 参照）
        ├ VSBL   u16 1（表示）
        ├ MASK   u16 0
        ├ SCLS   タグ + u32 0 + u8 2 + u32 145 + u32 50 + 3B（サイズ欄なし。未解明。2 = 中央揃え?）
        ├ CSTR   タグ + u16 個数(8) + 24.8 × 8 = (100, 0, 100, 0, 0, 0, 幅 1720, 高さ 163)
        │        高さ 163 = 113 + 移動量 50 と一致（推定）
        ├ ESET (文字数 + 1)
        └ MCHR × (文字数 + 1)   最後は文字コード 0 の終端
```

### XTRS（イン/アウト効果）

`kind` 1〜4 × `dir` 0(イン)/1(アウト) の 8 件。サンプルで位置を持つのは kind 1 だけ。

| オフセット（ペイロード） | 値 | 意味 |
|---|---|---|
| +0 | u16 1 | ver |
| +2 | u16 1〜4 | kind（対象） |
| +4 | u16 0/1 | イン / アウト |
| +8 | u32 30 | 長さ（フレーム） |
| +12 | u32 1 | 不明 |
| +24 | u16 2/0 | 2 = 移動あり（このとき続けて 24.8 ×6 = 位置A(x,y,z), 位置B(x,y,z)）|
| 続き | u8 0, u32 100 ×6 | 倍率 %（開始/終了 × xyz?） |
| 続き | 0×23, u16 100, u16 100 | 不透明度 %（開始/終了?） |
| 末尾 | VIDT (32B, 全 0) + 4B | 未解明 |

位置A = テロップの位置 (134, 1042)、位置B = 位置A + MVP_ の移動量（イン: y 992 / アウト: y 1092）。
= 「上から 50px スライドイン、下へ 50px スライドアウト、各 30 フレーム」と読める（推定）。

## フォント

.ts1 にフォント名は入っていません。`ACTP` と各グリフに **VWS 内部のフォント番号 1119 (0x45F)** があるだけです
（サンプルのフォントは「ウィン L7」とのこと）。フォント番号と名前の対応表は VWS 側の設定にあると思われます。
ただしグリフのアウトラインそのものはファイル内にあるため、フォントが無くても見た目は再現できます。

## RCHR / WVCT（グリフ）（確認済）

Windows GDI `GetGlyphOutline(GGO_NATIVE)` とほぼ同じ形式で、セル高 2048（ascent 1802 + descent 246）。
座標は整数、y は下向き（ベースライン = 0）。

```
"RCHR" u32 size | u16 1 | u16 使用回数 | u16 0 | u32 フォント番号 | u32 0 | u32 文字コード
"WVCT" u32 (size-8) | u32 輪郭データ長 | 60B ヘッダ | 輪郭…
  ヘッダ: u16 輪郭数, u16 1, bbox(l,t,r,b) 24.8 ×4, u16 2048, u16 2048, u16 黒枠幅, u16 黒枠高,
          u32 フォント番号, u32 文字コード, i32 ascent, i32 -descent, ABC幅 (A,B,C), u32 0
  輪郭:   u32 1, u32 以降のバイト数, i32 x, i32 y (始点)
          { u16 種別(1=直線, 2=2次スプライン), u16 点数, (i32 x, i32 y)×点数 } …
```

## レイアウト・描画（見本画像とのピクセル照合で確認済）

- 文字送り = 文字サイズ（全角セル 100px）。ACSP は「その文字の直前」の間隔に加算
- 行の幅 = 文字数 × 文字サイズ + 2 文字目以降の ACSP の合計
- 行は CSML.x から幅 CSTR.width (1720) の枠で **中央揃え**
- CSML.y がベースライン。グリフは 2048 セル → 文字サイズ px に等倍縮小
- 縁 = 外側 6px・角は丸（文字面の下に敷く）
- 塗りは非ゼロ規則
- 照合結果: 16 文字すべて ±0.25px 以内、縁幅 6.0px、全体誤差 1.96%（アンチエイリアス差程度）。
  VWS の描画は数式上の位置から (-0.125, -0.375)px ずれる（ラスタライザの画素中心の扱いの差と思われる）
