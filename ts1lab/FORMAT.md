# VWS テロップファイル (.ts1) 構造メモ（非公式・解析中）

3 種類のサンプルと、こちらで作った確認用ファイルを VWS で開いてもらった結果をもとに解析したものです。

| 呼び名 | 内容 | 裏付けに使えるもの |
|---|---|---|
| **見本** | 単一行 16 字・ニューロダン B 100px・白文字＋青縁 6px（内蔵フォント番号 1119） | VWS の書き出し PNG（画素単位で照合） |
| **別サンプル** | 2 行・ロダン Pro B 110px・「さん」だけ 85%・専用空白・白文字＋橙の縁＋影・フォント表つき（`test_1_swap.ts1` / `test_1_dup.ts1`） | 画像は無い。`OFRI`（描画範囲）と突き合わせ |
| **1 行もの** | 「実験①」〜「実験⑤」の 5 本。3 字・ニューロダン EB 150px・白文字・縁なし（内蔵フォント番号 1121）。入れ物が `CSSL` / `RUCH` / `USCU` の別の型。5 本の違いは最後の 1 字と保存時刻・履歴だけ | 画像は無い。`OFRI` と、Windows の字形との照合 |
| **確認用（第 1 回）** | 見本をもとにこちらで作った 6 本（打ち替え・縁 3px・縁 10px・サイズ 60・位置・色）を VWS で開いて書き出した PNG | 画素単位で照合 |

「確認済」は解析→再構築のバイト一致、または VWS 出力画像とのピクセル照合で裏付けが取れたもの、
「推定」はまだ裏付けがないものです。VWS が保存した 8 本すべてが解析→再構築でバイト一致し、全バイトを項目に割り当て済み。

VWS の PNG 書き出し（「変換・NA」）は、描画範囲 `OFRI` の左上から (幅 + 1, 高さ + 1) で切り抜いた画像になる
（全画面 1920×1080 の書き出しもある。見本の PNG は全画面だった）。VWS は開いたときに描画範囲を計算し直す
（こちらが書いた OFRI が違っていても、書き出しは VWS の式どおりの範囲になる）。

## 共通ルール（確認済）

| 項目 | 内容 |
|---|---|
| エンディアン | リトルエンディアン |
| チャンク | 4 文字タグ + `u32` サイズ（ヘッダ 8 バイトを含む）+ ペイロード |
| 例外 | `WVCT` のサイズはヘッダ 8 バイトを含まない。`ESET` は `"ESET" + u32 0 + u16 件数` の 10 バイト固定。`EMTR` は `"EMTR" + u32 文字コード + 12 バイト 0` の 20 バイト固定 |
| 数値 | 座標・サイズの多くは **24.8 固定小数点**（`i32 / 256`） |
| 文字列 | `u8 長さ`（0 のときは続く `u16` が長さ）+ `FF FE` + UTF-16LE + `00 00` |

### XTRS（イン/アウト効果）

`kind` 1〜4 × `dir` 0(イン)/1(アウト) の 8 件。サンプルで位置を持つのは kind 1 だけ。

| オフセット（ペイロード） | 値 | 意味 |
|---|---|---|
| +0 | u16 1 | ver |
| +2 | u16 1〜4 | kind（対象） |
| +4 | u16 0/1 | イン / アウト |
| +8 | u32 30 | 長さ（フレーム） |
| +12 | u32 1 | 不明 |
| +24 | u16 2/0 | 2 = 移動あり（このとき続けて 24.8 ×6 = 位置A(x,y,z), 位置B(x,y,z)）|
| 続き | u8 0, u32 100 ×6 | 倍率 %（開始/終了 × xyz?） |
| 続き | 0×23, u16 100, u16 100 | 不透明度 %（開始/終了?） |
| 末尾 | VIDT (32B, 全 0) + 4B | 未解明。別サンプルには VIDT が無い（省略できる） |

位置A = テロップの位置 (134, 1042)、位置B = 位置A + MVP_ の移動量（イン: y 992 / アウト: y 1092）。
= 「上から 50px スライドイン、下へ 50px スライドアウト、各 30 フレーム」と読める（推定）。

## MCHR（1 文字）（確認済）

```
"MCHR" u32 size | u16 1 | u16 グリフ番号(ORMP 内の RCHR の添字) | 22B (0)
[ DAAR: u16 1, u16 子数, 属性チャンク… ]   ← 書式変更がある文字だけ
"EMTR" u32 文字コード 12B(0)
```

属性チャンク（先頭文字が全部持つ。以降は変更点のみ）

| タグ | 値 | 意味 |
|---|---|---|
| ADCO | 4 + 50B × 件数 | 装飾。u16 ver, u16 件数 + 50B × 件数（下表）。見本 2 件、別サンプル 4 件 |
| AFIN | u32 0 / 1 | 未解明（見本 0、別サンプル 1） |
| ACTP | u32 | フォント番号。見本 0x45F = 1119（VWS 内蔵の番号）、別サンプル 0xE8A1DFA0（ODTT のフォント表を引く） |
| ACSZ | 24.8 ×2 | 文字サイズ 幅・高さ（見本 100、別サンプル 110） |
| AFLF | u32 4 | 未解明（両方 4） |
| ASLP | 24.8 ×2 | 未解明（両方 0。斜体角?） |
| AROT | u32 0 | 未解明（両方 0。回転?） |
| ALSP | 24.8 | 行間。行送り = 文字サイズ + 行間（別サンプル: 110 + 15 = 125px で OFRI と一致） |
| ACMG | 24.8 ×2 | **倍率 %（横, 縦）**。字形も送りも縮む。別サンプルは「さん」だけ 85%（確認: OFRI と一致） |
| ACSP | 24.8 | 字間 px。**その文字の直前**の間隔に効く（見本画像で確認済）。行頭の値は無視 |

属性は **変わった文字にだけ書かれ、書かれていない文字は直前の値を引き継ぐ**（ACSP・ACMG で確認）。属性の並び順はファイルによって違う。
終端（文字コード 0）や改行にも ACSP が付くことがある。

特別な文字コード: `U+000D` = 改行（空の字形を持つ）、`U+E73E` = 専用の空白（空の字形、送り 512 = 全角の 1/4）、`U+0000` = 終端。

## 1 行もの（CSSL）の型（確認済: 5 本とも解析→再構築でバイト一致）

「実験①」〜「実験⑤」は、見本と入れ物が少し違う。中身の考え方は同じ。

| 見本の型 | 1 行ものの型 | 違い |
|---|---|---|
| `CSML` | `CSSL` | 先頭の並び（ver, x, y, -1, 0, 1）は同じ。**x = 行の左端**（枠が無い）。行は x から右へ並ぶ |
| `CSTR` 個数 8（…, 枠の幅, 枠の高さ） | `CSTR` 個数 2 と書かれているが値は 4 つ: (0, 0, **行の幅**, 0) | 行の幅 = 字送り（1/256px へ切り捨てたもの。下の「VWS の描き方 1」）の合計 + 2 字目以降の字間。例: 150 × 3 + 1 + 4 = 455 から、3 字の字送りの切り捨てぶん 4/256 を引いた 454.984375（5 本とも 1/256px まで一致） |
| `SCLS` … u8 2, u32 145, u32 50 | `SCLS` … u8 4, u32 0, u32 50 | 意味は未解明（揃えや枠の種類か） |
| `XTRS` の中に `VIDT`（36 バイト） | `VIDT` が無い（XTRS は 164 / 140 バイト） | ほかの並びは同じ |
| （無い） | `RBID`（u16 ver, u32 4, 16 バイト 0）、`PROP`（u16 ver, u32 4, 14 バイト 0）、`EASG`（u16 ver, 16 バイト 0） | `SRSC` と `VSBL` の間に RBID、`MASK` と `SCLS` の間に PROP・EASG。未解明 |
| `RCHR` | `RUCH` | 中身は同じ並び。`WVCT` のあとに **u32 コード数 (1) + u32 文字コード** が付く |
| `MCHR` は `EMTR` で終わる | `EMTR` のあとに `USCU`（22 バイト: u16 ver, u32 1, u32 コード数 1, u32 文字コード） | 文字コードの控え。合字や異体字のためと思われる（推定） |
| （無い） | SWRK 直下に `MSCR` | 未解明 |

位置の例: x = 732.5078、行の幅 454.9844 → 中心 = 960.0（画面の中央）。文言を変えるときは中心を保って x と行の幅を書き直す（`TS1.rebuild`）。
1 行ものの各字には `ACSP`（字間）が 3 / 1 / 4 / 3（終端）と入っている。行頭と終端の値は並べ方に効かない（行の幅 = 150 × 3 + 1 + 4）。
行頭と終端が同じ値なのは別サンプル（−2 と −2）も同じで、「基準の字間」が入っていると思われる（推定）。

**往復（TS1 → Photoshop → PSD → TS1）は、1 行ものでは元のファイルとバイト単位で完全に一致する**（実験① で確認。
PSD の隣にある元の .ts1 を雛形にし、行頭と終端の字間は雛形の値を残す）。

## フォント

.ts1 のフォントの持ち方は 2 通りあります。

- **内蔵番号**（見本・1 行もの）: `ACTP` と各グリフに VWS 内部のフォント番号があるだけで、フォント名は入っていない。
- **フォント表つき**（別サンプル）: 番号は 0xE8A1DFA0 のような 32bit 値で、`ODTT` に 番号 → 太さ・文字セット・書体名「FOT-ロダン Pro B」・
  PostScript 名「RodinPro-B」が入っている。番号の決め方は不明（書体名の CRC32 / FNV / MD5 / SHA1 などの一般的なハッシュではない）。

分かっている内蔵番号（どちらも、Windows の字形と 1 点残らず一致することで確定）:

| 番号 | フォント | Windows の書体名 | 縦位置のずれ |
|---|---|---|---|
| 1119 (0x45F) | フォントワークス ニューロダン Pro B | `FOT-ニューロダン Pro B` | 183 |
| 1121 (0x461) | フォントワークス ニューロダン Pro EB | `FOT-ニューロダン Pro EB` | 183 |

VWS が表示したフォント名で分かった番号（字形は B のまま番号だけ変えた .ts1 を VWS で開いて確認。2026-11-13）:

| 番号 | VWS の表示 |
|---|---|
| 1113 | ニューロダン L |
| 1115 | ニューロダン M |
| 1117 | ニューロダン B（1119 と同じ表示。ユーザーが VWS の表示どおりに記録したもの。1119 との違いは未確認。DB の番号は見つかっていない） |
| 1123 | ニューロダン UB |
| 1114・1116・1118・1120・1122・1124 | 「不明な書体」（VWS にこの番号のフォントが無い） |

奇数の番号にニューロダンの太さが並んでいる（L 1113 / M 1115 / B 1117 / B 1119 / EB 1121 / UB 1123）。

送り幅は字形ごとの ABC 幅（A + B + C）で決まる。全角は 2048、専用空白 U+E73E は 512。半角文字もこの値で送られるはず（推定）。

VWS は表示にはファイル内の字形データを使い、フォント名の表示・打ち替えには番号を使う
（番号を変えずに字形だけ別フォントにした .ts1 は「見た目は変わるがフォント名は元のまま」になった）。

### .ts1 からフォントを特定する方法（`run.resolve_font` / `gdiglyph.identify`）

.ts1 には字形データそのものが入っているので、**同じ手順で作った字形と 1 点残らず一致するフォント**を探せば特定できる。
`to-ps` / `text` / `info` / `to-ts1` / `identify` のどれでも、.ts1 を読むたびに自動で行い、結果を `フォント表.json` に書く。

1. ファイルの中にフォント表（`ODTT`）があれば、その書体名・PostScript 名を使う
2. Windows に入っている全フォント・全部の太さと斜体（この PC で 1,327 通り）を em 2048 の字形データにして、
   .ts1 の中のそのフォント番号の字すべてと比べる。全部調べても 1 秒かからない。縦位置のずれもこのとき決まる。
   一致したフォントから 書体名・太さ・PostScript 名（フォントの name テーブル）を取る
3. 同じ字形のフォントが複数あるとき（Pro と ProN、等幅版とプロポーショナル版など）は、字幅（A・B・C）や黒枠まで同じものに絞る。
   それでも複数なら「候補が N つ」として全部覚えておき、**同じ番号の別の .ts1 を読むたびに候補を絞っていく**
   （区別できる字 — JIS2004 で形の変わった漢字や欧文 — が入っていれば 1 つに決まる）
4. どれも一致しなければ、`フォント表.json` / `run.KNOWN_FONTS` に登録済みの名前を使う。それも無ければ「不明」。
   `identify` はこのとき形の近さ（塗りの重なり）で候補を出す。`font-name 番号 名前` で手で登録もできる

確かさの試験: この PC の日本語フォントから無作為に 60 個ずつ 2 回（文言を変えて。延べ 120 個）選び、それぞれで字形データを作って .ts1 に入れ、当てさせた。
外れは 0。88 個は 1 つに特定、29 個は「同じ形の兄弟フォントが 2 つ」（Std / StdN、Pro / Pr6N、等幅 / プロポーショナル、
同じフォントの別名）、3 個は試験の文言の字を持たず対象外。

限界: そのフォントが PC に入っていなければ、字形からは特定できない（ODTT も登録も無い内蔵番号の場合）。
フォントの入っている PC（VWS の端末など）で一度読めば `フォント表.json` に残るので、その表を持ってくればよい。
TrueType 形式（.ttf）のフォントで VWS が同じ手順を使っているかは、サンプルが無く未確認（OpenType の 2 書体で確認）。

### ベースラインのずれ（確認済）

VWS の字形の y = 0（CSML.y の高さ）は、フォント本来のベースラインと一致しない。
ニューロダン B・EB では、フォントのベースラインが **183/2048 セル上**（100px で 8.9px 上）にある。
→ Photoshop のテキストのアンカー y = CSML.y + oy × 文字サイズ / 2048（見本: 1042 → 1033.05。oy = −183.26 は輪郭の重ね合わせで実測した値）。
PSD → TS1 は逆に引く。これを入れないと Photoshop の文字が一律 9px 下にずれる。
183 の出どころは不明（フォントの数値からは説明がつかない。otmAscent 1802 / otmDescent −246、tmAscent 2540 / tmDescent 655）。
フォントごとに違う可能性があるので、そのフォントの字形を持つ .ts1 から実測して `フォント表.json` に持つ。

### Photoshop 側の注意（確認済）

- Photoshop の既定のカーニング「メトリクス」は、かなのペアを詰める（見本 16 文字で合計 14px、オプティカルだと 51px）。
  VWS は全角を常に文字サイズ送りで並べるので、JSX ではカーニングを「0（手動）」にしている。
- PSD の文字スタイル（EngineData）にはカーニング方式の区別が残らない（手動でも `AutoKerning: True`）。
  効いた結果は TySh の `bounds`（組み幅）に出るので、PSD → TS1 ではこれを「全角送り＋トラッキング」の計算幅と比べて、
  2px 以上狭ければ警告する。
- Photoshop のアンチエイリアスは STRONG が VWS に最も近い。境界線の太さは Photoshop が保存時に整数へ丸める。
- PSD の一番上の画像レイヤは `vwsrender.py` で描いた VWS と同じ絵。保存した PSD を Photoshop で開いた表示は、VWS の PNG と 1 画素も違わない（見本で確認）。
- スクリプトで非表示のテキストレイヤを `activeLayer` にすると表示に切り替わる（検証で画像を書き出すときに注意）。
- 2 行以上のとき、Photoshop のアンカーは 1 行目のベースライン（VWS の y は最終行）。
- Photoshop は、水平比率を掛けた字でもトラッキングには比率を掛けない。中央揃えは行末のトラッキングも行の幅に数える。
- 専用空白 U+E73E（全角の 1/4）は 1/4 em 空白 U+2005 に対応させる。

## RCHR / RUCH / WVCT（グリフ）（確認済: VWS が作った字形とバイト単位で同じものを作れる）

```
"RCHR" u32 size | u16 1 | u16 使用回数 | u16 0 | u32 フォント番号 | u32 0 | u32 文字コード
"WVCT" u32 (size-8) | u32 輪郭データ長 | 60B ヘッダ | 輪郭…
  ヘッダ: u16 輪郭数, u16 1, bbox(l,t,r,b) 24.8 ×4, u16 2048, u16 2048, u16 黒枠幅, u16 黒枠高,
          u32 フォント番号, u32 文字コード, i32 ascent, i32 -descent, ABC幅 (A,B,C), u32 0
  輪郭:   u32 1, u32 以降のバイト数, i32 x, i32 y (始点)
          { u16 種別(1=直線, 2=2次スプライン), u16 点数, (i32 x, i32 y)×点数 } …
（RUCH はこのあとに u32 1, u32 文字コード）
```

VWS は Windows GDI の `GetGlyphOutlineW(GGO_NATIVE)` から次の手順で作っている。
見本 15 字・1 行もの 3 字（計 1,372 点とヘッダ）が 1 バイトも違わず再現できる（`gdiglyph.py`）。

1. em の高さ 2048（`lfHeight = -2048`）でフォントを選ぶ。アセント / ディセント = `otmAscent` / `otmDescent`（ニューロダンは 1802 / −246）
2. 各点を整数にする: **x = floor(x)、y = floor(−y − ずれ)**（GDI は y 上向き。ずれ = フォントごとの定数。ニューロダン B・EB は 183）
3. **曲線は 1 レコード 2 点（制御点 1 + 終点 1）**。GDI の 2 次スプラインは制御点が続くので、隣り合う制御点の中点を
   整数にしたあとの値で `(a + b) / 2`（0 方向へ切り捨て）として作り、2 点ずつのレコードに分ける
4. 輪郭は **逆回り** にして書く（始点 = GDI の最後の点）。直線が続く所は 1 つの直線レコードにまとめる（点数は 1〜27 を確認）
5. ヘッダ: bbox = 整数にした点の範囲（制御点を含む）、黒枠の幅・高さ = `GGO_METRICS` の `gmBlackBoxX / Y`、
   A・B・C = `GetCharABCWidths` の値

**3 点以上の曲線レコードを書くと VWS で字が崩れる**（確認用の第 1 回で確認）。VWS は曲線レコードの先頭 2 点だけを読み、
残りの点を読み飛ばす（崩れた字の VWS 書き出しが、この読み方で 99.99% 再現できる）。
フォントファイルから fontTools で輪郭を作る方法（`FontGlyphSource`）は、点の位置が VWS と少し違う近似。
Windows にそのフォントが入っていれば GDI から作る（`run.glyph_source`）。

## レイアウト・描画（VWS の書き出し PNG と画素単位で照合済み）

- 文字送り = 字形の A・B・C（左の余白・字の幅・右の余白。2048 単位）を、文字サイズ × 横倍率で px にしたもの。
  **VWS は 1/256px の整数で並べ、A・B・C を別々に切り捨ててから足す**（下の「VWS の描き方 1」。全角でも 0〜2/256px 短くなる）。
  全角は A + B + C = 2048、専用空白 U+E73E は 512。半角英数・半角空白も同じ式。ACSP は「その文字の直前」の間隔に加算
- 行の幅 = 送りの合計 + 2 文字目以降の ACSP の合計
- **複数行**: 一番長い行を CSML.x から幅 CSTR.width の枠の中央に置き、**各行は左端をそろえる**（行ごとの中央揃えではない。2 行の書き出しで確認）。
  CSSL では x が行の左端
- CSML.y が最終行のベースライン。行送り = 文字サイズ + ALSP
- グリフは 2048 セル → 文字サイズ px に縮小（ACMG の倍率があれば横・縦それぞれ掛ける。横 85% で 1 画素も違わない）
- 塗りは非ゼロ規則（見本では偶奇規則でも同じ結果）

### VWS の描き方（`vwsrender.py` に実装）

VWS が書き出した PNG と、1 画素も違わないもの（2026-11-13 時点。確認用 31 本と見本の 32 枚中 28 枚）:
見本、確認用の 縁 2・3・4・5・6・7・8・9・10・12・14・20px、サイズ 30・60、位置（縦の端数つきも）、色（黄/黒、暗い灰/白）、
打ち替え（新しく作った字）、横 85%、字間 20、2 行、8 行、空白入り、半角入り、ニューロダン EB の枠つき、
縁なしの 1 行もの（VWS のファイルそのまま・打ち替え）。
残り 4 枚: 縁 1px（99.75%。191 画素が 1/255 違う。下の 8 の色の丸め）と、原点がちょうど 1/8px の境目に乗った字が
1/8px 左に出るもの 3 枚（21_半角入り・32_字送り調べB・34_半角のあと。下の 1 の「未解決」）

以下の 1〜8 をこの順に行う。単位は「8 倍格子」= 1px を 8 等分した整数。

1. **字の原点**: VWS は横の位置を **1/256px の整数**（.ts1 の 24.8 固定小数点と同じ単位）で持つ（`TS1.layout_fx`）。
   - 字送り = floor(A × k) + floor(B × k) + floor(C × k)。A・B・C は字形ヘッダ +44 からの i32 × 3、k = 文字サイズ × 横倍率 × 256 / 2048。
     **3 つを別々に切り捨てる**ので、全角（A + B + C = 2048）でも 0〜2/256px 短くなる（サイズ 100 は k = 12.5 で、奇数の値 1 つにつき 0.5 失う）。
     これが積もって 7〜8 字目あたりから 1/8px 左に見える（以前「1 字ごとに 0.01px 詰まる」「0.9999 倍」と見ていたものの正体）
   - 字間 ACSP は 1/256px のまま足す。行の幅 W = 字送りの合計 + 2 字目以降の字間
   - 枠つき（CSML）: 行の左端 = 枠の x + floor((枠の幅 − 一番長い行の W) / 2)。各行は左端をそろえる。1 行もの（CSSL）: 行の左端 = x
   - 原点の 8 倍格子: 横 = floor(x / 32)（1/8px へ切り捨て）。縦 = floor(ベースライン y × 8)（縦も切り捨て。
     40_縦の端数 = y に 20/256px 足したもので確認: 四捨五入なら 1/8px 下がるはずが、VWS の絵は足す前と同じ）
   - 枠の x の端数（1/256px 単位）も効く: 31（行の左端 % 32 = 31）と 32（同 0）で、式どおり 1/8px 違う位置に出た

   裏付け: (a) VWS が保存した 1 行もの 5 本の「行の幅」（116476 / 256）が、この式の合計と 1/256px まで一致。
   (b) 確認用 18 本・249 字のうち 248 字の原点が一致（字ごとに VWS の PNG と合う原点を求めて照合。`vwstest.py origins`）。
   丸め方の総当たり（A・B・C それぞれ 切り捨て・四捨五入・切り上げ など 6 通り）でも、3 つとも切り捨て以外は外れが増える。

   **未解決（原点がちょうど 1/8px の境目に乗った字が、特定の位置でだけ 1 マス左に出る）**:
   第 3 回の 31〜34 で、字のせいでも字送りのせいでもないと分かった。
   - 31（全部の字の x % 32 = 31）は全字が式どおり → 字送りが式より長い字は無い（「で」「グ」「ガ」「ひ」「が」、半角のあとの「で」も）
   - 32（x % 32 = 0）は、x = 594.0px の字だけが 1/8px 左（1 行目の 3 字目の「い」と、2〜6 行目の 3 字目。どれも同じ x）。
     同じ行の 394・494・694・…・1494px の字は式どおり。3 字目が左でも 4 字目は元に戻るので、積み重ねの誤差ではない
   - 34（21 の「で」を「い」に替えたもの）も同じ x = 1049.0px で 1/8px 左 → 字ではなく場所
   - x % 32 = 0 の位置 30 か所（のべ 44 字）のうち、左に出るのは 594.0 と 1049.0 の 2 か所だけ（枠は 134 + 1720 で同じ）。
     580.375・595.5・644.0・1035.0・1149.0 などは式どおり
   - 位置 x を一度別の単位に直して戻す形（x / c × c、x × c / c、x × (1/c) × c。基準は 0・枠の左/中央/右・行の左/中央/右・960。
     c は 2〜8192 と その 1/10・1/100、32 ビット/64 ビット）を総当たりしたが、この 2 か所だけが下がる c は無い。
     画面の座標変換の形（x × 2/W − 1 → 戻す。W = 1920 ほか）も合わない
   - 影響は「その 1 字が 1/8px 左」だけ。実装には入れていない
2. **輪郭の点**: `(int)(fx + 座標 × 文字サイズ × 8 / 2048)`。fx は原点の画素内の位置（0〜7。縦も同じく fy）。
   つまり「原点のある画素の左上」を基準にした座標で整数にする（C の整数変換 = 0 方向へ切り捨て）。そのあと原点からの相対座標に戻す。
   3 の曲線の中点もこの座標で計算する（原点が画素の境目なら `(int)(座標 × 倍率)` と同じ。サイズ 150・ベースライン .5 の字の下端で分かった）
3. **曲線**: 2 次ベジェ (p0, c, p1) を整数のまま半分ずつに割る。
   - 割るかどうか: `h = p0 + (p1 − p0) / 2 − c`（弦の中点と制御点の差。割り算は C の整数割り算 = 0 方向へ切り捨て）を x・y それぞれ求め、
     **hx² + hy² > 17 なら割る**（17 は割らない・18 は割る、まで確認）
   - 割り方: `q0 = (p0 + c) / 2`、`q1 = (c + p1) / 2`、`r = (q0 + q1) / 2`（どれも足してから 2 で割る整数割り算）→ (p0, q0, r) と (r, q1, p1) に同じ処理
   - 割らないときは p0 → p1 を直線で結ぶ。サイズ 30・60・100・150 で同じ式
4. **塗り**: できた多角形を 8 倍サイズで GDI と同じ規則で塗る（整数座標の点が内側なら塗る。左と上の辺は含み、右と下は含まない）
5. **1 ラインぶんの文字面** m = 1 画素の 8×8 = 64 点のうち塗られた数（0〜64）
6. **上下 2 ラインを足す**: k[y] = m[y] + m[y+1]（0〜128）。そのうえで字ごとに描く範囲を切る:
   字ごとの絵には枠があり、枠の外は描かれない。枠は、描いた多角形ではなく輪郭データの点（制御点も含む）の範囲を実数のまま置いて決まる:
   - 上: floor(上端の px − 0.5) の行から描く（2 ライン足しのぶん 1 行広い）。以前の「切り上げて 1 行上」は、上端 − 0.5 が
     ちょうど整数のときだけ 1 行多かった（41_EB の「の」= 上端 954.5px。VWS は 954 行目から、旧式は 953 行目から）
   - 左: 左端の px（1/256px の x + 輪郭の左端 × 倍率）を切り捨てた列から描く。輪郭の点は 0 方向へ切り捨てるので、
     字によっては多角形が 1/8px だけ手前の画素にはみ出すが、そこは枠の外で描かれない
     （245 字で確認: はみ出した 16 字は全部描かれず、ほかは全部描かれる。以前の「左端 + 1/8 を切り捨て」は位置の式が違っていたための見かけ）
7. **縁**: 文字面 k を 1px 刻みでずらしたコピーの最大値。ずらし量の形は円 i² + j² ≤ T では表せない（20px は (5, 20) が入って
   (20, 5) が入らない）ので、**縁幅ごとの実測の形を表で持つ**（`vwsrender.EDGE_ROWS`。行 j ごとの最大の |i|）:

   | 縁 | 行 j = 0, 1, 2, … の最大の i |
   |---|---|
   | 1 | 1, 1 |
   | 2 | 2, 2, 1 |
   | 3 | 3, 3, 2, 1 |
   | 5 | 5, 5, 5, 4, 4, 2 |
   | 6 | 6, 6, 6, 5, 5, 4, 2 |
   | 10 | 10, 10, 10, 10, 9, 9, 8, 8, 7, 5, 3 |
   | 14 | 14, 14, 14, 14, 14, 13, 13, 12, 12, 11, 10, 9, 8, 6, 4 |
   | 20 | 20, 20, 20, 20, 20, 19, 19, 19, 19, 18, 18, 17, 16, 16, 15, 14, 13, 11, 10, 8, 5 |

   表に無い縁幅は 円 i² + j² ≤ (縁 + 0.62)² で近似（10・14px と同じ形になる値。4・7〜9・11〜13・15px 以上は 1 段ずれる可能性）。
   円・楕円・正 N 角形・角度を刻んで点を打つ方法・8 倍格子の円・GDI の楕円リージョンを試したが、8 つ全部に合うものは無かった
8. **重ね方**: 縁の層（縁色、Ae = min(255, 2 × 縁の k)）の上に文字面の層（文字色、Af = min(255, 2 × 文字面の k)）を重ねる:
   - アルファ A = Ae + ((255 − Ae) × (Af + 1) >> 8)（63 万画素で 1 つも外れない。縁なしなら Ae = 0 で A = Af）
   - 色: Af = 0 なら縁色。それ以外は w = (Af × 255 + 1) // A として 縁色 + ((文字色 − 縁色) × (w + 1) >> 8)（>> は負でも切り捨て）。
     縁が不透明なら w = Af で、全部の色が一致（暗い文字は Af = 0 の所を縁色にしないと 1 ずれていた）。
     縁が半透明の所に文字面が重なる画素（縁 1・2px の細い所）だけ、1/255 ずれることがある（約 3%。整数の手順は未確定）

`render.py` は旧モデル（被覆率で塗る近似）で、`ts1tool.py compare` の当てはめ（位置・縁幅の目安）にだけ残している。

影（装飾の種別 1）の描き方は、画像つきのサンプルが無いので未解明。縁なし（1 行もの）の描き方も画像では未確認（式は同じと仮定）。

### 描画範囲 OFRI の式（確認済: VWS が保存した 8 本と、確認用を VWS が計算し直した範囲のすべてと一致）

字形の範囲（輪郭データの点。制御点も含む）を、丸める前の位置（1/256px の整数で並べた x。8 倍格子へ切り捨てる前）に置いたときの外接範囲を (L, T, R, B)（実数）、縁を e として:

```
left   = floor(L + 1/8) − e
top    = floor(T − 0.5) − e
right  = floor(R + 1/8) + 1 + e
bottom = floor(B + 0.5) + 1 + e
```

横は 1/8px ぶん右へ寄せてから切り捨て、縦は四捨五入（上は 2 ライン足しのぶん 1 行広い）。描いた結果の画素範囲とは 1px 違うことがある。
top は字ごとの枠の上端と同じ式にそろえた（T − 0.5 がちょうど整数のときだけ以前の式 ceil(T − 0.5) − 1 − e と 1 違う。
OFRI でその場合に当たる実例はまだ無い）。
影があるとき（別サンプル 1 件だけ）: right に 影の広がり（太さ 4 + 追加 4 = 8）、bottom に 影の広がり + 1 を足すと一致する。
先頭の 40 / 3 / 113.0 は 3 種類のサンプルで同じ値。

### リソース（ORMP）

- **グリフ番号（MCHR +10）は ORMP の添字**（リソース全体の通し番号）。グリフだけが先頭に並ぶファイルでは
  グリフの並び順と同じだったが、字ごとに装飾を変えたファイルでは色・グラデーションがグリフの間に挟まる（`TS1.glyph_at`）。
  リソースは「文字列を後ろから前へたどって、初めて出てきた順」に並ぶ（終端 → 最後の字 → … → 先頭の字。装飾の色は、その装飾を持つ字の直後）
- **CRGB の +10 の u32 は使用回数**（その色を指している装飾の層の数）。以前「色種別」と読んでいた。
  例: 「二色」の茶色は 2 つの装飾 × 2 層 = 4
- **CGRD = グラデーション**: u16 版, u16 使用回数, 6 バイト（0）, u8 色の数 n, 色 4 バイト × n（CRGB と同じ並び）, 位置 u8 × n（0〜255）,
  [WPF1 = 模様の画像], 末尾（0 が並び、… 04 00 00 00 00 00 05 00 … と続く。未解明）。
  例: 「金」= 6 色 #B39A1E → #FFDF17 → #F1F273 → #F1F273 → #FFDF17 → #B39A1E、位置 0・51・102・153・204・255。
  PNG では文字面の上から下へこの順に変わる（縦のグラデーション）
- **CPTN = 模様**: u16 版, u16 使用回数, 6 バイト（0）, WPF4 = 模様の画像, 末尾

### 模様の画像の圧縮（WPF0。`wpf.py` に実装）

資料は見つからなかった（ネットで「Photron」「NITRO」「ts1」「TSRC SWRK ORMP」「WPF0」を調べたが、形式の説明は無い）。
装飾サンプル 3 本の全データから解いた。**3 本とも「画像に戻す → 圧縮し直す」が元のバイト列と 1 バイトも違わない**（`python wpf.py selftest`）。

入れ物: `WPF1`（グラデーションの中）/ `WPF4`（模様 CPTN の中）, u32 長さ の中に
`WPF0`, u32 種類, u16 幅, u16 高さ, u32 1, u32 24, u32 L, 面のデータ, `ff ff ff ff`。
L = `WPF0` のタグから `ff ff ff ff` の終わりまでの長さ。CGRD はこのあと 82 バイト続き（未解明。最後の 4 バイトは L の控え）、CPTN はここで終わる。

- 種類 17: 面 1 枚（濃淡）。種類 3: 面 4 枚（かすれ模様。4 枚とも別の絵。どう使い分けるかは第 5 回で確かめる）
- 面は上の行から、行ごとに独立したバイト列（行の頭は必ずバイト境界）。2 面目以降の 1 行目は前の面の最終行を「真上」とする
- 行の 1 バイト目 = 行の種類
  - 0: 生の行。続く 幅 バイトが各画素の（画素 − 真上）mod 256
  - 1: 続く 1 バイト d。行の全画素が 真上 + d
  - 2: 続く 1 バイトが先頭画素の（画素 − 真上）。そのあとビット列（各バイトの上位ビットから）で 2 画素目以降の差分。最後は 0 で埋めてバイト境界へ
- 差分 = 画素 − (左 + 上 − 左上)（mod 256）。D[x] = 画素 − 真上 とすると 差分[x] = D[x] − D[x−1]
- 字句:

| ビット | 意味 |
|---|---|
| 000 | 差分 0 |
| 001 / 010 | +1 / −1 |
| 011 nnnn | 差分 0 が n + 3 個（3〜17）。nnnn = 1111 なら続く 8 ビット e で 18 + e 個（18〜273） |
| 10 s m | ±(2 + m) |
| 110 s mm | ±(4 + m) |
| 1110 s mmm | ±(8 + m) |
| 1111 bbbbbbbb | 差分そのもの（1 バイト）。11111111 は「行の残りは全部差分 0」 |

  s = 1 が負。負のとき m の各ビットは反転して入る
- 圧縮する側の決まり（元と同じバイト列にするため）: 0 は 3 個以上なら連続の字句、18 個以上は 8 ビットのほう（273 個ずつ）。
  行の最後の 0 の連続は「行の残りは 0」。字句で書いた行が 2 + 幅 × 0.9 バイトを超えるときは生の行（種類 0）にする
  （網点のサンプル: 圧縮で残った行は最大 1722 バイト、生にされた行は圧縮すると 1732 バイト以上。幅 1920）

道具: `python run.py texture 素材.ts1`（PNG に取り出す）、`python run.py texture-in 素材.ts1 画像.png [番号] [面]`（差し替え）。
同じ画像で差し替えると元のファイルとバイト一致する。

### 模様つきグラデーションの色の決まり方（縞・二色の PNG で確認）

### 第 4・5 回で確定したこと（2026-11-13。VWS の PNG と 1 画素も違わないものだけ）

- **層の不透明度**: 不透明度を 0 にした層は描かれない。層のアルファ = 文字面のアルファ × 不透明度 ÷ 256 の切り捨て（`a * op >> 8`）。
  57（赤の内側の縁 70% = 180）・60（二色の模様 50% = 128）が全画素一致
- **斜体（ASLP の 1 つめ = 角度 度）**: 縦横に拡大した座標で x − y × tan(角度)（y は下向き正）。拡大の前に傾けると、縦横の倍率が違う字
  （二色の数字 130 × 138%）で合わない。55（赤の文字面だけ）・60 が全画素一致。字ごとの枠の左端は「傾けたあとの点の左端」
- **字ごとのベースラインの下げ（MCHR +30。24.8 固定小数点）**: 二色の大きい数字 2 字（14.0）が 14px 下に描かれる。60 で確認
- **太さが負の縁（赤の内側の縁 −1）= 文字面を 1px 削る**: 3 × 3 の最小値（文字面の量 k のまま削ってからアルファにする）。57 が全画素一致
- **層の上下の重なり**: 下の層は、上の層の形（不透明度 0 でも）の内側が抜かれて描かれる（59・58 で、文字面 + 縁の範囲が抜けている）。
  縁が 2 重のときの外側の縁（赤の白 5px の下の黒 4px）は、内側の縁の外からさらに広がる（合計 9px）ように見える（式は未確定）
- **種別 4 = 四角く広げる縁**: 文字面の量 k を (2 × 太さ + 1) の正方形のずらしで最大値をとる（丸い縁 = 種別 9 とは別）。
  上の層（文字面）の形で抜く: アルファ = max(0, 縁のアルファ − 文字面のアルファ)。二色の 61 が 25146 画素すべて一致
  （VWS のアルファを超えない「ずらし量」を逆算すると、ちょうど −4〜4 の正方形になる）
- **縁は上の層の外側から広がる**: 二色の白い縁（太さ 4・追加 5）は、四角 4 + 縁 3 の外からさらに 4px（左の縦棒で 7px 抜けて、その外に縁）
- **追加分（extra）= ぼかし**: 二色の 62 は、縁の外側が 1px あたり 255 / 11 ずつ薄くなる = 幅 11（2 × 5 + 1）の箱型の平均。
  縦棒の真横の断面は「平均を切り上げ」で 1 の位まで一致。全体の式（ぼかす前の形・角の扱い）は第 6 回で決める
- 模様は面 0 だけが使われる（77 で面 0 を方眼にすると模様が消え、78 で面 1 を方眼にしても見た目は変わらない）
- こちらで圧縮し直した模様（71）・色の数を変えたグラデーション（73）・装飾つきの打ち替え（74・75）は VWS で正しく開く
- AFIN を 0 にしても字の並びは変わらない（76）。AFIN は字詰めではない。縞・金の字の並びが式と違う理由は別にある（未解明）
- 金の文字面（種別 0x801）は、字の上端から下端まで縦にグラデーションがかかり、上側に明るい縁が乗る。太さ 0 にすると白一色（52）。式は未確定
