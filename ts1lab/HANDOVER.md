# VWSフォトショブリッジツール 引き継ぎメモ（クラウドセッション → PC のセッション）

VWS のテロップファイル（.ts1）と Photoshop を相互変換する実験の、現時点の状態です。
新しいセッションはまずこのファイルと [FORMAT.md](FORMAT.md)、[README.md](README.md) を読んでください。

## 目的（ユーザーの要望）

1. .ts1 を解析して Photoshop で再現する（編集できるテキストレイヤとして）
2. Photoshop で作ったテロップを .ts1 で書き出して VWS で使う
3. フォントを正しく特定・設定する（最優先）

## VWS の描き方を特定（2026-11-12。`vwsrender.py`）— VWS の PNG と 99.998% の画素が完全一致

ユーザーの「目指せ 99.9%」を受けて、VWS の PNG の画素値から描き方を逆算した。`_再現.png` / `_確認.png` / PSD の画像レイヤは `vwsrender.py` で描く。
見本で色のある 120,056 画素のうち **VWS の PNG と違うのは 2 画素（差 2/255）だけ**（その前の版は 99.57%、さらに前の `render.py` は 81%）。
保存した PSD を Photoshop で開いたときの表示も、VWS の PNG と 2 画素違うだけ（`見本.psd` で確認）。

確定したこと（手順の全体は FORMAT.md「VWS の描き方」と `vwsrender.py` の冒頭）:
1. VWS は 8 倍サイズの整数格子に GDI と同じ規則で塗っている。輪郭の点は `(int)(座標 × 8)`（0 方向へ切り捨て）
2. 塗りの規則 = 整数座標の点で内外判定（numpy では多角形を +0.5 ずらして中心判定にすれば同じ。本物の GDI と全点一致を確認）
3. 字の原点: 行の先頭字からの距離 × 0.9999 を 1/8px に四捨五入（7 字目で 1/8px の段差）
4. **曲線の割り方（最後まで残っていた点）**: 整数のまま半分ずつ割る。割るかどうかは
   `h = p0 + (p1 − p0) / 2 − c`（整数割り算 = 0 方向へ切り捨て）で **hx² + hy² > 17 なら割る**。
   中点は `(a + b) / 2`（足してから割る）。見本の曲線 309 本・判断が画像から確かめられる 702 か所が例外なくこの式どおりで、
   式を探すのに使わなかった字（て・い・で）も一致した
5. 上下 2 ラインの足し算 k[y] = m[y] + m[y+1]。字ごとに上端を整数行に丸め、その上にはみ出す行は切る
6. 縁 = k のずらし重ねの最大値（i² + j² ≤ 41〜44）
7. 色 = floor(縁色′ + (文字色′ − 縁色′) × k / 128)、アルファ = min(255, 2k)。色′ は 8bit 値 + (R 0.90〜0.95, G 0.81, B 0.10)。見本の 129 色すべて再現

曲線の式にたどり着くまでの記録（同じ所で迷わないために）:
- 「2 階差分 p0 − 2c + p1 の 2 乗和 ≤ 68」は 702 か所中 12 か所で外れる（全体 99.65%）。和・最大・重み付き・実数・2048 単位・
  制御点と弦の距離・面積・角度・長さの差・中間点の 1 次結合（総当たり）・「4 等分してから間引く」・中点の丸め方の変種は、どれも合わない
- 外れ方に「奇数のとき、進む向きに減速していれば切り上げ・加速していれば切り捨て」という癖があるのが決め手だった。
  これは弦の中点を `p0 + (p1 − p0) / 2` と書いたときの整数割り算の丸めそのもの
- 調べ方: VWS の PNG から 色 → k を逆引き → 下から m[y] = k[y] − m[y+1]（負になったら 0）で 1 ラインぶんの塗り m を逆算 →
  曲線ごとに「どこで割ったか」（分割の木）を総当たりで当てはめて、正解の割り方を集める → それを説明できる式を探す。
  調査用スクリプトは作業用一時フォルダにあり、リポジトリには入れていない

残っている 2 画素: 「な」の輪郭の先端の 1 点（8×8 のうち 1 点）。輪郭を閉じる辺と最初の曲線がつながる頂点ちょうどの点を
VWS は塗らず、本物の GDI は塗る。1 例しかないので規則は不明（別の文言の VWS の PNG があれば調べられる）。

Photoshop のライブテキスト側の設定（STRONG など）と PSD の構成は変えていない。新しい描画で `見本.psd`・`見本_打ち替え.psd` を作り直し、
PSD → TS1 の往復も確認済み（見本は「値 0 の冗長な ACSP が 1 か所無い」だけ、打ち替え版は差分 0）。
OFRI（描画範囲）は実際に描いて求めるようにした（`vwsrender.drawn_bbox`）ので、見本・別サンプルとも 4 辺が元のファイルと一致する
（以前は左端が 1px ずれていた）。これに合わせて `VWS確認用\` の 6 本と zip も作り直した（変わったのは OFRI の 1px だけ）。
`ts1tool.py compare` は、最初に `vwsrender` での画素単位の一致度を出すようにした（その後ろは旧モデルでの当てはめ）。

## 別サンプルで分かったこと（2026-11-12）

PC 内にあった別の .ts1（NITRO 調査時の `tools\telop\nitro\test_1_swap.ts1` / `test_1_dup.ts1`。2 行・110px・一部 85%・専用空白・
橙の縁＋影・フォント表つき）を解析に使った。詳しくは FORMAT.md。要点:
- `ODTT` = フォント表（番号・太さ・文字セット・書体名・PostScript 名）。内蔵番号でないフォントのときにある
- 送り = 字形の (A + B + C) / 2048 × サイズ × 横倍率。専用空白 U+E73E は 512。改行 = U+000D。行送り = サイズ + ALSP
- `ACMG` = 文字ごとの倍率 %。`ACSP`・`ACMG` は書かれていない文字では直前の値を引き継ぐ
- `ADCO`: +33 = 有効/無効、+30 = 太さへの追加分、種別 1 = 影（縁の外に右下へ広がる）
- `OFRI` = 実際に描かれた画素の範囲。先頭の 40 / 3 / 113 は固定値
- 3 本とも selftest 全項目 OK（解析 → 再構築でバイト一致）

## 注意

- 実機（VWS）での確認は本番データを避け、テスト用の環境で行う
- 色は B G R A 順（`ts1core.COLOR_ORDER`）。見本の縁は青 #122FE7。VWS の PNG 書き出しでの色の入れ替えは無い
- **ユーザーから VWS の書き出し PNG が来たら、聞き返さずに PNG を正解として自分で照合・判断する**（ユーザーの希望）。
  `ts1tool.py compare` で .ts1 と、Photoshop の出力（COM で JSX を実行して PNG 保存）とも直接比べる。PNG から分からないこと（VWS 上のフォント名表示など）だけ聞く
- 字間（ACSP）は「その文字の直前」に効く。Photoshop のトラッキングは「その文字の後ろ」なので 1 文字ずらして変換している
